# 第十六轮：压缩与第三方托管依赖

从 runtime 固定基线中的源码编译 `System.IO.Compression.Native` 包装层、zlib-ng 2.2.5 和 Brotli，使用 devkitA64/libnx。zlib-ng 先采用通用实现，未启用需另行验证的平台优化路径。未修改这些第三方源码。

链接脚本加入压缩静态库，并随 NRO 保存 .NET、第三方声明、zlib-ng、Brotli 以及探针提供的额外许可证。本轮使用与游戏一致的 `ZstdSharp.Port 0.8.8`，许可证取自 NuGet 元数据指定的上游提交 `2cd0c019693bc786a5fe5c3be94e107b24e7267e`。

## 构建依赖修正

原先只构建主程序集后调用 IlcCompile，没有收集发布依赖，导致 ILC 未加载 ZstdSharp。现增加固定 SDK 的 `_ComputeResolvedCopyLocalPublishAssets` 和 `_ComputeAssembliesToCompileToNative` 步骤，再编译目标文件；没有调用 Linux 的原生链接步骤。

实验工程设置 `IlcResilient=false`，避免缺失类型/程序集被转换为“调用时总是抛异常”的方法体。最终响应文件确认包含 ZstdSharp.dll，代码生成成功且无此前缺程序集诊断。

运行时构建脚本也补齐 devkitA64 的 PATH，使 Ninja 重新运行 CMake 时能够找到交叉工具。

## 验证结果

- zlib、gzip、Brotli 和 ZstdSharp 流接口各完成 65536 字节往返校验。
- 目标端解码由宿主 Python/zlib 独立生成的固定 zlib 样本。
- 修改 zlib 校验和后，正确触发 InvalidDataException。
- 最后将压缩测试与此前 GC、线程、任务和文件测试合并运行，全部启用阶段通过，返回 0。

阶段 25–28 均为 65536，阶段 29=1。基础产物归档 `artifacts/libnx/managed-probe/compression-basic-pass`，完整产物归档 `compression-full-pass`，许可证也已归档。

这没有验证真实 main.rsb、所有压缩格式边界、吞吐性能、游戏或真机。下一轮继续 SHA-256 等资源校验功能。
