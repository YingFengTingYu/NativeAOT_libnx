# 第十三轮：编译器生成的循环 GC 检查点

## 失败对照

新增托管探针在工作线程内执行无分配、无方法调用的循环，主线程强制压缩 GC。独立原生看门狗两秒后释放循环，避免测试永久挂起。使用官方代码生成器及从本仓库构建的未添加检查点版本时，均先触发看门狗，再结束 GC，返回 114。

反汇编确认原始循环仅有计数、原子读取和回跳，没有 GC 检查点。当前 libnx PAL 使用返回地址劫持，无法仅靠它暂停一直不返回的该循环。对照归档在 `artifacts/libnx/managed-probe/gc-poll-stock-failure`。

## 编译器修改

为 RyuJIT 增加默认关闭的 `LibnxLoopGcPolls` 选项，仅在 ARM64 NativeAOT ABI 下启用。在现有 `fgInsertGCPolls` 阶段标记指向较小/相同块编号的普通控制流边，复用上游 GC poll 降低过程、`RhpTrapThreads` 和 `RhpGcPoll`，由编译器生成相应 GC/EH 信息。

宿主代码生成器使用 GCC 12 从源码编译。另一个独立提交限定了 `gentree.h` 两处与字段同名的枚举类型，解决 GCC 类型名查找歧义，没有放宽编译错误检查。

```sh
docker run --rm -v "$PWD:/runtime" nativeaot-libnx-build:10.0.11 bash ports/libnx/build-host-jit.sh
```

构建产物为 `artifacts/libnx/host-jit/current/libclrjit_universal_arm64_x64.so`。脚本本轮复用了已存在的主机 CMake 配置；首次配置分支未通过清除现有缓存另行重跑。

托管构建需同时设置 `LibnxJitPath` 为该 Linux 宿主库在构建容器中的绝对路径，`LibnxLoopGcPolls=true`；继续保留 `--noinlinetls`。公共设置在 `Libnx.NativeAOT.targets`，实验工程也提供相同属性。

## 通过结果

启用选项后，反汇编确认循环内生成了 trap 标志检查及 GC helper 分支。先通过基础循环测试，再运行完整托管压力测试：循环对象图、移动 GC、终结器、显式异常、两个工作线程和 128 次线程生命周期均通过。

最终完整测试连续三次通过。忙循环持有的数组在 GC 前后地址不同，恢复后内容保持正确，看门狗没有超时：

```text
managed.stage.141=0
managed.stage.142=63
managed.stage.143=1
managed.stage.14=1
managed.result=0
native.pass=1
```

归档在 `artifacts/libnx/managed-probe/gc-poll-full-pass-1` 至 `gc-poll-full-pass-3`。汇编对照在 `artifacts/log/libnx/busy-loop-stock-asm.txt` 和 `busy-loop-polls-asm.txt`。

仍未证明所有复杂控制流形状均覆盖，也未评估该保守插入方式的性能开销。隐式硬件异常、完整基础类库、游戏和真机继续保持未验证状态。
