# 第九至十轮：移动 GC、终结器与托管工作线程

第九轮在 PvZ_Ultimate 的独立托管探针中通过了循环对象图、移动 GC（观察到数组地址变化）、16 个终结器和 32 次嵌套显式异常测试。归档在 `artifacts/libnx/managed-probe/gc-stress-pass`。

第十轮增加 `SystemNative_CreateThread`，并在 Eden v0.2.1 中验证两个真实 C# 工作线程：

- 新线程的整数和对象线程静态变量初始为空，各线程写入不同值。
- 三个托管线程 ID 不同，线程运行期间 ID 保持不变。
- 工作线程等待期间，主线程进行强制压缩 GC。
- 两个工作线程各完成 64 轮数组分配和内容检查，各触发 8 次强制压缩 GC；主线程同时触发 8 次 GC。
- 线程静态数组和工作线程栈上的数组内容正确，两个 `Join` 成功。

这里的“同时”指多个应用线程请求 GC；仍使用 WorkstationGC，并且关闭后台并发 GC。

## 事件等待停滞与修复

最初使用 libnx `UEvent` 时存在不稳定失败。GDB 抓到一个工作线程已退出，另一个停在 `Thread::WaitForGC`；此时 `RhpTrapThreads=0`，GC 完成事件已置位。一次运行也出现过成功，不能用它判断稳定性。

事件适配改为 libnx `Mutex` / `CondVar`，将每个等待者是否已获得信号保存在受锁保护的等待节点中。手动重置不会撤回已授予等待者的信号；自动重置每次只释放一个等待者。没有使用需要额外权限的 `svcCreateEvent`，也没有用定时重试跳过 GC 等待。

修改后原生内存/事件测试通过，包括新增的 64 轮双等待者 `Set` 后立即 `Reset`。完整托管测试连续三次通过，记录在 `artifacts/libnx/managed-probe/thread-event-pass-1` 至 `thread-event-pass-3`。旧路径失败记录和调试栈分别在 `thread-first-failure` 与 `artifacts/log/libnx/thread-gdb.txt`。这些证据尚不能单独确定旧路径的问题属于 libnx、模拟器还是二者与暂停操作的交互。

```text
managed.stage.10=2
managed.stage.11=128
managed.result=0
native.pass=1
```

## 仍需继续

当前线程创建先经过 Newlib pthread。libnx v4.12.0 的 `newlib.c` 将 `__syscall_thread_detach` 标记为未实现，因此线程资源回收还不能算完成，下一轮替换这一创建路径并测试重复创建/退出。隐式硬件异常、无调用忙循环的 GC 进展、完整基础类库、游戏和真机仍未验证。
